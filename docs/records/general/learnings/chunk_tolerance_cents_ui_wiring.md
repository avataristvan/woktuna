FFT partial search tolerance UI wiring chunk complete (commit 8902cf6), directly analogous in scope to the reference-pitch UI-wiring chunk (which it explicitly mirrored). fft-peak-picking.ts's detectPartialsByFftPeakPicking already accepted `{ toleranceCents? }` (Chunk 6) but nothing above it exposed it. FftPartialDetector gained a constructor param (`toleranceCents?: number`) plus a runtime `setToleranceCents(cents: number): void` setter (mutable at runtime, not fixed at construction, since the app may already have a live mic session running). ToneFieldApp (bootstrap.ts) gained `setToleranceCents(cents: number): void`, delegating straight to `partialDetector.setToleranceCents(cents)` — no re-render call needed, confirmed by reading analyze-tone-field.ts: `tick()` calls `analyzeToneField.analyze()` every rAF frame, which calls `partialDetector.detectPartials()` fresh each time, reading the mutable field live (same render-loop pattern as reference-pitch and hammer-mode). UI in main.ts: `#tolerance-cents-input` number input (min=50/max=500/step=1, default 250) with a `#tolerance-cents-presets` datalist offering 150/250/350 cents -- 250 is DEFAULT_TOLERANCE_CENTS, 150/350 bracket it as narrower/wider, chosen using fft-peak-picking.spec.ts's empirically-measured real cutoff (between 248-250 cents) so the presets are meaningfully different rather than arbitrary. Same revert-on-invalid validation as reference-pitch (reverts to `lastValidToleranceCents` closure var on non-finite/out-of-range input). style.css: reused the existing `#reference-pitch-input` rule by adding `#tolerance-cents-input` to its selector list (repo convention here is ID-specific rules, not a shared reusable class). DEFAULT_TOLERANCE_CENTS's docblock updated to note it's now user-adjustable via this UI -- default value/behavior unchanged. One deliberate exception to this repo's 'infrastructure/ adapters get no unit tests' convention: partial-detector.spec.ts was added (3 new tests, integration-style with synthetic signals, no mocks) since the task explicitly invited it and it was cheap to verify -- synthesizes an octave detuned 270 cents (just past the default tolerance's measured cutoff, inside 350) and asserts both the constructor param and the runtime setter actually change the detection outcome. 132/132 tests passing (was 129, +3), build/lint/typecheck all clean.
