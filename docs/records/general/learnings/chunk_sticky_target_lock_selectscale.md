Sticky target-note lock added to SelectScale (application/select-scale.ts, commit 1c9b804) to fix user-reported live-hardware symptom: displayed target note jumping to a different (usually lowest/Ding) note as a struck note decayed or neighboring resonance bled in, because nearestTargetFor() re-resolved fresh via nearestTarget() every rAF tick with no memory. Now SelectScale holds an internal lock ({note, targetHz}, not centDeviation which stays live). A call only relocks (re-runs nearestTarget()) when detectedHz drifts more than STICKY_LOCK_RELOCK_THRESHOLD_CENTS=175 (unverified heuristic, same tunable-constant status as fft-peak-picking.ts's DEFAULT_TOLERANCE_CENTS -- needs real-hardware validation) from the locked targetHz; otherwise it returns the locked note/targetHz with centDeviation freshly recomputed via a locally-duplicated centsBetween() (nearest-target.ts doesn't export its own, kept the existing capability-boundary duplication convention). Lock resets on setActiveScale()/setReferencePitchHz() since a lock from the old scale/reference pitch is meaningless after either changes. Public nearestTargetFor() signature/return type and bootstrap.ts's call site are unchanged -- this is fully internal statefulness. select-scale.spec.ts is the capability's first application-layer test (previously only domain/ and infrastructure/dsp/ had co-located specs per this repo's convention) -- justified as a deliberate exception since lock/relock/reset behavior across sequential calls isn't expressible as a pure-function domain test. 137/137 tests pass (132 existing + 5 new), build/lint/typecheck clean. Does NOT fix the root-cause autocorrelation octave/subharmonic misdetection in autocorrelation.ts -- that remains a separate, unscoped DSP concern; this only mitigates the symptom at the scale-configuration layer. Still needs the user's real-hardware smoke test to confirm the fix actually helps live.
