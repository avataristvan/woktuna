Capability-centric DDD + clean architecture, per user's standing convention. Each capability under src/capabilities/<name>/ is layered domain -> application -> infrastructure(/presentation), dependencies point inward, domain has ZERO Web Audio/Canvas/DOM dependency (that's what makes the tuning-rule logic unit-testable and is the actual differentiating IP). Three capabilities: scale-configuration (note/frequency conversion, nearest-target lookup against a known handpan scale), tone-field-detection (autocorrelation for fundamental + band-limited FFT peak-picking for octave/compound-fifth relative to the detected fundamental -- no library does this, hand-rolled and highest-risk), tone-field-visualization (pure deviation-to-guidance mapping encoding the physical rules, then a Canvas renderer as the only DOM-touching part). Capabilities stay decoupled from each other's domains; composition happens in app/bootstrap.ts and application/build-guidance.ts. shared-kernel/partial-kind.ts holds vocabulary both detection and visualization depend on (PartialKind, axis mapping, expected ratios).
